# B13 — one recorded-data aggregation and factual summary policy

Branch develop/yuankang-wei. BC-11; no migration/shared/browser database change. Developer self-check PASS; peer review/UAT PENDING.

SummaryRepository groups owner/nondeleted records by stored recordDate in PostgreSQL. It reads canonical decimal snapshots only, never legacy kcal floats or current profile weight. SUM(NULL) remains null; counts retain record presence, known/missing values and known values from LEGACY_UNVERIFIED records. Source activation/AI eligibility does not filter saved records. Activity minutes include valid recorded durations even when energy is unavailable. SummaryService uses one repeatable-read database snapshot across food/activity/weight/target reads and supplies all today/daily/weekly/trends handlers. There is no separate controller algorithm.

Per metric: absent records -> hasData=false/knownSum=null; all missing -> hasData=true/knownSum=null/missing>0; real zero -> knownSum=0 with knownValueCount>0. partial means a mix of known and missing values; all-missing is distinguished by null plus counts. legacyValueCount counts known legacy values, not unknown measurements. Each average uses its own days with a known daily sum, including true zero; no calendar-day or food-count denominator substitution. Daily timeline preserves null gaps. Exact BigDecimal sums; average alone receives final HALF_UP3.

Only scalar current dailyTargetKj is read from profile. No automatic maintenance/deficit fallback or target-intake+activity allowance remains in any formal handler. Goal comparison uses current explicit target on known-intake dates, explains the historical/current-reference distinction and never fills unrecorded meals. CalorieTargetCalculator and old response records remain deprecated source-history classes without Spring bean/API consumers. No current algorithm calls them.

RuleSummaryService emits reproducible fact codes/values: recorded coverage, known totals and per-metric denominators, activity minutes, current target reference, previous equal-length range average differences where both sides have known data, and measured weight change within selected dates. No comparable data yields insufficiency, not0. Differences are arithmetic between published recorded-day averages, with both denominators/ranges exposed; no population/health inference. Weight facts preserve exact decimal from/to/change values; approximate one-decimal display is rounded once and explicitly labelled. No model/safety-consent gate or medical wording is used.

Canonical public shapes match P02: DaySummary{day,goalComparison,facts}, PeriodSummary{rangeStart,rangeEnd,calendarDayCount,days,totals,averages,goalComparison,facts}, WeeklySummary{current,previous}. daily requires date; weekly requires actual end and compares two7-day ranges. trends accepts a complete1..366-day from/to OR days shortcut (default7), rejects ambiguity/incomplete/future/invalid ranges. All endpoints use active Session USER owner. Clock/IANA defaults shared with records. An outage is a structured read failure, never fake empty data.
